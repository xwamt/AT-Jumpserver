# 为什么连接仍要 5–8 秒，以及下一步怎么砍

**Date:** 2026-08-27  
**Status:** Proposal（针对「每次连资产终端 5–8s、体感无提升」）  
**Branch:** `cursor/perf-optimize-impl-fb4b`（已合的树缓存 / 高亮 / keep-alive **不会**把这条冷路径压到 2s）

依据：源码瀑布、KoKo/Luna/core master（2026-08）、官方文档与 issue。

---

## 1. 为什么感觉不到提速

已经落地的优化（client 池、Bearer 复用、endpoint 缓存、有 cookie 时跳过 HTML、树 memoize）主要帮：

- **同窗口第二次连接**（内存里已有 sessionid）
- 资产树展开、刷新、终端刷屏

**每次点资产仍要 5–8s**，因为冷路径形状没变，而且会话全在内存里：

1. 发布版仍是 **0.1.9**。perf 分支若未装进编辑器，keep-alive / warmup 提前退出都用不上。
2. `JumpServerSession.connect()` 仍是串行：`detail → token → endpoint → warmup（无 cookie）→ WS`。
3. Cookie / Bearer / client 池在 **Reload Window / 重启 VS Code** 后全部清空。每天第一次、每次 reload 都是全冷路径。
4. `token_reusable: false`，**每一次连接都 POST 新 connection-token**。
5. 日志 `finished in Nms` **不包含** KoKo 对目标机的 SSH 拨号。用户看到「Connected」到出现 shell 提示符之间还有 0.5–2s+，客户端砍不掉。

### 请先看 Output「AT JumpServer Terminal」

把日志级别调到 Debug，连一次，看：

| 行 | 含义 |
|---|---|
| `REST bearer login` 还是 `reused` | 每次都 login ⇒ 窗口刚 reload 或 client 没复用 |
| `KoKo warmup login in Nms` | N 就是 Django 表单段；每次连接都出现 ⇒ session 从未跨次存活 |
| `KoKo terminal connect for … finished in Nms` | 只到 WS open。若 N≈2s 而体感 6s，差值多半是 **KoKo→资产 SSH** |
| `asset detail reused` / `KoKo endpoint reused` | 没有这些行且扩展版本是 0.1.9 ⇒ 还没跑到 perf 构建 |

## 2. 5–8 秒大概花在哪（VPN RTT 80–200ms）

| 段 | 估时 | 每次都付？ |
|---|---|---|
| Bearer 登录（首次，可能 JSON+form） | 0.4–1.2s | reload 后是 |
| asset detail GET | 0.2–0.6s | 同资产可缓存 |
| **createConnectionToken POST**（ACL+取密） | 0.3–1.0s | **是** |
| smart endpoint GET | 0.2–0.4s | 同堡垒可缓存 |
| **Django 表单 warmup**（拿 sessionid） | **1.5–3.5s** | reload 后是 |
| KoKo WS 新 TCP+TLS（可能另一 host） | 0.4–1.0s | **是** |
| **KoKo SSH 到资产**（日志之后） | 0.5–2s+ | **是，物理下限** |

HTML `/koko/connect/` **不是** KoKo WS 的协议前置：现代 Luna 是 SPA 路由，内嵌工作台甚至不经过该页。扩展现在走它，只是为了给 `/koko/ws/terminal/` 备 Django Cookie。

当前扩展 WS URL 是 `/koko/ws/terminal/?token=<令牌id>`。现代 KoKo **已删除** 旧的免登录 `/koko/ws/token/?target_id=`。握手认证（2026-06 之后的 KoKo）为三选一：

1. `sessionid` + `csrftoken` Cookie（3.x / 4.x 全线可用）
2. `Authorization` + `Date` + `X-JMS-ORG`（AccessKey HMAC 或 Bearer）—— **约 2026-06 才进 KoKo**
3. 连接票据 `ticket`（`POST /koko/api/connect-ticket/`，同样新）

没有 Cookie、也没有新版头/票据时，握手会被 302 到登录页。所以「无 cookie 先试 WS」在老部署上只会白付一次失败往返。

---

## 3. 建议落地（按收益）

目标：冷连接 **≈1.5–2.5s**（剩余 = token + WS + 资产 SSH）；reload 后接近同窗口二次连接。**做不到「瞬时」**——KoKo 必须向 core 换密钥再 SSH 目标机。

### 必做

**R1. 分步计时**  
`connect timings: detail= token= endpoint= warmup= ws= total=`（禁止打 token URL / Cookie）。没有数据不要猜。

**R2. 把 `sessionid`+`csrftoken` 存进 SecretStorage（按堡垒）**  
reload 后跳过整段表单（**1.5–3.5s**）。密码已在 SecretStorage，模型自洽。401 / WS 失败再走现有 warmup。这是对 2026-08-20「不持久化 Cookie」的**有意翻转**，需产品点头。

**R3. 连接内并行**  
`getAssetDetail`（含 Bearer）启动后：无 cookie 则 `ensureWebSession()`（只打 `/core/auth/login/`，不依赖 token）与后续 REST 重叠；detail 就绪后 `createConnectionToken` ∥ `endpoints/smart/?protocol=https&asset_id=`（失败再回落 `token=`）。

**R4. 选中资产时预热登录**  
已有 300ms detail prefetch，成功拿到 client 后 `ensureWebSession()`。不要在 activate 对所有堡垒登录。

**R5. WS 握手传入 REST 的 keep-alive Agent**  
仅当 `endpoint.host` 与 `baseUrl` 同主机。多数单机部署省 **0.2–0.6s** TLS。

### 按数据再做

**R6. 记住上次成功账号**  
列表缓存没有 `permed_accounts`，不能纯离线跳过 detail；可把上次账号写入 globalState，token 与 detail 并行，4xx 再回退。

### 明确不做

| 项 | 原因 |
|---|---|
| 无 cookie 直连 `/koko/ws/terminal/` | 老 KoKo 必 Cookie；失败 +0.3s |
| 切回 `/koko/ws/token/?target_id=` | master 已删该路由 |
| 默认 `is_reusable` / `token_reusable` | 需管理员开 `CONNECTION_TOKEN_REUSABLE`；30 天可复用等于长期直连凭据 |
| hover 预取 connection-token | 一次性令牌、审计噪音、R3 后边际小 |
| 等 socket 再开 webview | 会把 xterm 加载加回关键路径（现已并行） |
| 默认 AccessKey 头认证 / connect-ticket | 仅 2026-06+ KoKo；用运行时探测再开，不要按版本号写死 |

更安全的长期凭据是 **AccessKey HMAC**（可吊销、可 IP 白名单），用它即时创建**一次性** connection-token，而不是把资产令牌做成可复用。

---

## 4. 批次

1. R1 计时（单独小 PR，建立基线）
2. R3 + R5（纯客户端；`asset_id=` 先探针）
3. R2 Cookie 入 SecretStorage（产品确认后）
4. R4 预热（依赖 `ensureWebSession`）
5. R6 看 R1 里 detail 是否真慢

验收：同一堡垒 reload 后再连，日志不应再出现 `KoKo warmup login`；`finished in Nms` 应落到 1–2s 量级，余下时间到 prompt 视为 SSH 地板。

## 5. 证据（摘要）

- KoKo 现路由无 `/ws/token/`，terminal WS 走 `HTTPMiddleSessionAuth`：Cookie / 头 / ticket。[koko webrouter + pkg/auth/http.go](https://github.com/jumpserver/koko)
- Luna 内嵌直接 `wss://…/koko/ws/terminal/?token=`，`/koko/connect` 是前端路由。[luna useTerminalSocket.ts](https://github.com/jumpserver/luna)
- `endpoints/smart` 接受 `asset_id`（也接受 token）。[terminal/api/component/endpoint.py](https://github.com/jumpserver/jumpserver)
- 一次性令牌默认 5 分钟；可复用需全局开关。[docs configuration](https://www.jumpserver.com/docs/configuration)
- Cookie 失败导致 connect 302：[Issue #13935](https://github.com/jumpserver/jumpserver/issues/13935)
